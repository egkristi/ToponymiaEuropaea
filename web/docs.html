Toponymia Europaea Documentation

An open, data-driven research framework for the systematic analysis of European place names across linguistic, historical, geographical, ecological, and cultural dimensions.

The standard is absolute: Every contribution must be scientific, verifiable, testable, and provable. Data requires references. Code requires tests. Claims require evidence.

What This System Does

  • Ingests place-name data from 14 connectors (GeoNames, Kartverket, Wikidata, OSM, Lantmäteriet, etc.)
  • Normalizes across scripts, orthographies, and languages (201 language modules)
  • Segments compound names into morphological components with confidence scores
  • Classifies language origin using phonological, morphological, and statistical evidence
  • Analyses through 21 independent research perspectives (15 coded modules)
  • Tests hypotheses using 12 statistical test families with mandatory robustness checks
  • Validates data integrity via SHA-256 checksums, schema validation, and 4,000+ automated tests

Architecture

Design Principles

  • Scientific rigour first — every claim is testable, every result is reproducible
  • Uncertainty is not optional — confidence intervals, not point estimates
  • Data provenance is sacred — every record carries source, license, and timestamp
  • Modularity over monoliths — language modules, connectors, perspectives are independently extensible
  • Fail loudly — validation errors halt pipelines, not produce bad data

Methodology

Epistemological Position

  • Place name interpretations are hypotheses, not facts
  • Multiple competing interpretations coexist with different probability weights
  • Uncertainty is quantified and propagated through all analyses
  • Claims are falsifiable through statistical testing

Data Pipeline Stages

  1. Ingestion — Connectors normalize heterogeneous sources into a common format
  2. Normalization — Unicode NFC, script detection, language-specific orthographic rules
  3. Morphological Segmentation — Compound head/modifier identification with confidence
  4. Language Classification — Phonological/morphological/statistical evidence for source language
  5. Etymological Generation — Candidates from lexical databases, sound change rules, ML models
  6. Statistical Testing — Hypotheses tested against null models with robustness checks

Statistical Methods

Permutation Testing

The primary statistical method. For each test:

  1. Compute observed test statistic
  2. Generate null distribution by permuting labels (not coordinates)
  3. Compute p-value as proportion of null values ≥ observed
  4. Report effect size and confidence intervals

Null Models

Test TypeNull Model
Element vs. signalElement labels randomly distributed among all places
Spatial clusteringRandom subset of same size from all places
Temporal consistencyRandom assignment of dates to places
Language boundaryRandom placement of boundary independent of topography

Robustness Requirements

Every test must survive:

  1. Regional jackknife — Conclusion stable when excluding 10% of data
  2. Bootstrap CI — Effect size confidence interval excludes zero
  3. Parameter sensitivity — Result stable across parameter choices
  4. Confound control — Population density, source density, terrain visibility

Synthetic Validation

Before applying to real data, every test must demonstrate:

  • Power ≥ 0.80 — Can detect a planted signal of realistic magnitude
  • FPR ≤ 0.10 — Does not reject null when data is pure noise

Multiple Testing Correction

  • Bonferroni correction (conservative)
  • Benjamini-Hochberg FDR (when tests are independent)
  • Both corrected and uncorrected p-values reported

Preregistration Protocol

  1. Formulate hypothesis before examining data
  2. Specify test method, null model, and significance criterion
  3. Record in analysis/preregistered/ with timestamp
  4. Execute test and report results regardless of outcome

Submission Process

  1. Register the source in databank/sources.jsonl
  2. Prepare JSONL file following databank/schema/attestation.v1.json
  3. Run batch validation: uv run toponymia databank validate --schema attestation
  4. Run dedup check against existing records
  5. Submit PR using the attestation template

Data Quality Stages

Every record progresses through 5 quality stages:

StageNameRequirements
1Candidate (Quarantine)Passes schema validation, has source citation
2VerifiedSource confirmed, coordinates validated, no duplicates
3EnrichedSegmentation, classification, and etymology attached
4ReviewedPeer verification by second contributor
5PublishedAuthoritative — included in analysis datasets
Demotion & Retraction: Records can be demoted or retracted at any time if new evidence undermines their validity. Retraction does not delete — a retraction note is attached and the record is excluded from analysis.

Adding a Language Module

Interface

from toponymia.languages.base import (
    BaseLanguageModule,
    SegmentationResult,
    LanguageClassification,
    EtymologyCandidate,
)

class MyLanguageModule(BaseLanguageModule):
    language_code = "xxx"      # ISO 639-3
    language_name = "My Language"
    family = "Language Family"
    branch = "Family > Branch"
    period = "Start-End CE"
    script = "Latn"            # ISO 15924

    suffixes = ["-suffix1", "-suffix2"]
    prefixes = ["prefix1-", "prefix2-"]
    stems = ["stem1", "stem2"]

    def segment(self, form: str) -> list[SegmentationResult]:
        """Break a name into morphological components."""
        ...

    def classify(self, form: str) -> LanguageClassification:
        """Assess probability that a form belongs to this language."""
        ...

    def etymologize(self, components) -> list[EtymologyCandidate]:
        """Generate etymology candidates for segmented components."""
        ...

Step-by-Step

  1. Research — Document common suffixes, modifiers, sound changes, and key references
  2. Create — src/toponymia/languages/your_language.py
  3. Implement segmentation — Match known suffixes (longest first), assign confidence
  4. Implement classification — Return confidence 0–1 with evidence
  5. Implement etymology — Provide meaning candidates for known elements
  6. Write tests — tests/test_languages/test_your_language.py
  7. Auto-discovered — No manual registration needed

Guidelines

  • Be conservative with confidence — understate rather than overstate
  • Document sources — each element should reference academic literature
  • Handle ambiguity — many elements are shared across languages (e.g., -berg)
  • Consider sound changes — OE -hām vs. -hamm distinction
  • Test with real, well-attested examples from scholarly literature

Pull Request Process

Universal Requirements (All PRs)

  1. All existing tests pass
  2. No linting errors (ruff check + ruff format)
  3. PR description explains what and why
  4. No unrelated changes bundled
  5. License-compatible content only

Additional Requirements by Type

Data Contributions

  • Full source citations for every record
  • Correct ISO 639-3 language codes
  • Plausible geographic coordinates (±5 km)
  • Temporal dating where available
  • Records enter as Stage 1 (Candidate)

Research Contributions

  • Testable claim with null hypothesis
  • Reproducible method (code + data + seed)
  • All sources cited
  • Honest confidence assessment
  • Synthetic validation: power ≥ 0.80, FPR ≤ 0.10
  • Preregistered before data examination

Code Contributions

  • Tests cover new functionality
  • Type hints on public interfaces
  • Follows existing architecture patterns

Review Criteria

Every PR is evaluated on five questions:

  1. Is it true? — Claims supported by evidence
  2. Is it testable? — Could be falsified in principle
  3. Is it reproducible? — Another researcher could replicate
  4. Is it honest? — Uncertainty acknowledged, limitations stated
  5. Is it attributed? — Sources and prior work credited

Ethics Framework

Core Principles

1. Respect for Indigenous and Minority Languages

  • All language layers are equally valid data
  • Never privileges a majority-language form as "correct"
  • Consults with relevant communities before publishing analyses of sensitive sites
  • Documents colonial and assimilation history explicitly

2. Acknowledging Historical Violence

Many European place name landscapes bear traces of forced renaming:

  • Norwegianization of Sámi and Kven names
  • Russification of Finnish, Baltic, and Ukrainian names
  • Germanization of Slavic names in Eastern Europe
  • Anglicization of Welsh, Scottish Gaelic, and Irish names
  • Hellenization of Slavic and Turkish names in Greece
  • Turkification of Armenian, Greek, and Kurdish names

These processes are documented as data (renaming events with actors and motivations), never hidden or normalized.

3. Disputed Territories

  • All attested name forms are recorded without privileging one
  • No automatic preference for the controlling state's official form
  • Temporal and political context is explicit
  • The project does not take political positions

4. Sacred and Sensitive Sites

  • Only included with community consent
  • Precise locations may be generalized when requested
  • Cultural protocols are respected

5. Responsible Publication

  • All results include confidence intervals and effect sizes
  • Analyses of ethnic/linguistic distributions are not suitable for political instrumentalization
  • The project explicitly disclaims support for ethno-nationalist readings
  • Findings about historical populations do not imply territorial claims

GDPR & Historical Person-Names

Place names frequently derive from personal names (anthroponymic toponyms). GDPR applies to identified or identifiable living natural persons only. It does not apply to deceased persons (Recital 27).

Project Policy

  1. >100 years dead: Freely usable as historical-linguistic data. No GDPR concern. Covers >99% of toponymic material.
  2. 10–100 years dead: Usable as geographic/linguistic data. Place name is a geographic designator, not personal data. Research exemption (Art. 89(1)) applies.
  3. Living persons: Rare. Record only geographic name from official gazetteers. No biographical data, no profiling.

Indigenous Languages

Place names in minority and indigenous languages represent living cultural heritage. The framework:

  • Treats all language layers as equally valid — Sámi, Kven, Romani, Basque, Sorbian, Cornish, Welsh, Breton, Catalan
  • Never privileges a majority-language form as "correct"
  • Documents forced renaming (fornorskning, Russification, etc.) as historical events with actors
  • Invites indigenous language communities as collaborators, not subjects
  • Supports language revitalization efforts where relevant
  • Respects sacred site protocols — locations generalized when requested

Compatibility Rules

  • CC0 + CC BY → CC BY (attribution required)
  • CC BY + ODbL → ODbL + Attribution (both obligations)
  • ODbL + CC BY-SA → Incompatible (different share-alike mechanisms)
  • Statistical outputs (aggregated findings) are not database derivatives — safe to publish freely
Record-level tracking: Each record carries its own license in the databank. The system can produce license-filtered exports for specific use cases.

Architecture Decisions

ADR-002: Phonetic Matching

Decision: Keep NordicPhoneticNormalizer; do not adopt Beider-Morse (BMPM).

  • Nordic normalizer: 36% TPR, 6.7% FPR, 10.8 µs/key
  • BMPM: 8% TPR, 13.3% FPR, 1506 µs/key — unsuitable for Nordic toponyms
  • Generic algorithms (Soundex, Metaphone, NYSIIS): 40-60% FPR — unacceptable
  • Future: language-family-specific normalizers for non-Nordic expansion

ADR-003: Coordinate Resolution

Decision: Multi-source coordinate resolution using strict priority hierarchy.

  • Priority: National mapping authority → National gazetteers → GeoNames → OSM → Wikidata
  • Conflict thresholds: <100m minor, 100m–1km moderate, >1km major
  • All source coordinates stored in provenance metadata
